# 04 · 实战示例：两个可直接改造的 Skill

> 示例 A 展示「最小可用」，示例 B 展示「完整形态」。示例中的 `SKILL.md` 正文按官方要求使用祈使句英文，说明文字用中文。

---

## 示例 A · 最小 Skill（只有 `SKILL.md`）

适合：流程简单、不需要脚本 / 长资料 / 模板的场景。

**路径**：`~/.codebuddy/skills/changelog-helper/SKILL.md`

```yaml
---
name: changelog-helper
description: Generate a Markdown changelog from git history. This skill should be used when users ask to write release notes, summarize commits between tags, or prepare a version changelog.
---

# Changelog Helper

## Overview

Generate a concise, grouped Markdown changelog from a commit range.

## When to use

Use this skill for changelog / release-notes requests that rely on git history.
Do not use it for rewriting an existing changelog file that the user already provided.

## Steps

1. Identify the commit range from the user request; default to the range since the latest tag.
2. Run `git log --pretty=format:'%h %s' <range>` to collect commit subjects.
3. Group entries into Features, Fixes, Docs, and Chores by their prefixes.
4. Output Markdown with the version heading first, newest group first, and one bullet per commit.
5. Preserve the original commit wording; do not invent changes that are not in the log.

## Output format

Produce a single fenced Markdown block containing only the changelog.
```

**为什么这样写**

| 片段 | 作用 |
| --- | --- |
| `name` | hyphen-case，与目录名一致 |
| `description` | 一句话能力 + `This skill should be used when…` + 三种典型场景 |
| `When to use` | 划清边界，避免抢别的技能 |
| `Steps` | 祈使句、可机械执行、含默认值与兜底 |
| `Output format` | 固定输出形态，减少每次结果差异 |

**触发语句示例**

- 「帮我写这一版的更新日志」
- "summarize commits since v0.1.0"
- 「把最近的提交整理成 changelog」

## 示例 B · 完整 Skill（三类资源齐备）

适合：流程较长、有确定性脚本、有格式规范、需要固定模板的场景。

### 目录结构

```text
~/.codebuddy/skills/release-notes/
├── SKILL.md
├── scripts/
│   └── collect_commits.sh
├── references/
│   └── format.md
└── assets/
    └── template.md
```

### `SKILL.md`

```yaml
---
name: release-notes
description: |
  Produce team-standard release notes from git history. This skill should be used when
  users ask to write release notes, generate a changelog for a version, or summarize
  commits between two tags or dates.
  Triggers: "写发版说明", "生成更新日志", "prepare release notes", "changelog since v1.0".
  Do not use for editing an already-written changelog file.
---

# Release Notes

## Overview

Collect commits, classify them, and render release notes that comply with the team format.

## Workflow

1. Resolve the commit range. Accept a tag, a tag pair, or a date range; default to the range since the latest tag.
2. Run `scripts/collect_commits.sh <range>` to obtain the raw commit lines. Treat its output as the single source of truth; do not invent entries.
3. Read `references/format.md` to obtain grouping rules, heading levels, and wording constraints.
4. Classify each commit into Features / Fixes / Docs / Chores. Move unmatched entries to Chores.
5. Copy `assets/template.md` and fill its placeholders with the version, date, and grouped entries.
6. Return the rendered Markdown only. Omit empty sections.

## Error handling

- To handle an empty commit range, report that no commits were found and stop.
- To handle a failing collection script, report the command output verbatim and stop; do not guess the history.
- To handle ambiguous version input, ask one concise clarifying question before proceeding.

## Resources

- `scripts/collect_commits.sh` — deterministic commit extraction.
- `references/format.md` — detailed format specification and examples.
- `assets/template.md` — output skeleton copied for every run.
```

### `scripts/collect_commits.sh`

```bash
#!/usr/bin/env bash
set -euo pipefail

RANGE="${1:-$(git describe --tags --abbrev=0 2>/dev/null || echo HEAD^)..HEAD}"
git log --no-merges --pretty=format:'%h %s' "$RANGE"
```

### `references/format.md`

```markdown
# Release Notes Format

## Grouping

| Prefix in subject      | Group    |
| ---------------------- | -------- |
| feat / feature         | Features |
| fix / bugfix           | Fixes    |
| docs / readme          | Docs     |
| chore / refactor / test| Chores   |

## Constraints

- Keep the original subject wording; strip only the conventional prefix.
- Use `##` for group headings and `-` for entries.
- Write dates as YYYY-MM-DD.
- Omit a group when it has no entries.
- Do not include merge commits or author names.
```

### `assets/template.md`

```markdown
# {{VERSION}} ({{DATE}})

## Features
{{FEATURES}}

## Fixes
{{FIXES}}

## Docs
{{DOCS}}

## Chores
{{CHORES}}
```

### 校验与打包

```bash
SKILL_CREATOR="/Applications/CodeBuddy CN.app/Contents/Resources/app/extensions/genie/out/extension/builtin/skill-creator"

python3 "$SKILL_CREATOR/scripts/quick_validate.py" ~/.codebuddy/skills/release-notes

```

### 运行时三层加载演练

```text
① 常驻：name + description（含中英文 Triggers）
        ↓ 用户说「帮我写 v1.2 的发版说明」→ 语义命中
② 加载：SKILL.md 正文（6 步流程 + 错误处理 + 资源清单）
        ↓ 按步骤引用
③ 执行 collect_commits.sh（无需读入上下文）
   读取 references/format.md（仅在需要分组规则时）
   复制 assets/template.md（用于产出，不读入上下文）
        ↓
输出：符合团队模板的 Markdown 发版说明
```

### 设计决策对照

| 决策 | 对应的原则 |
| --- | --- |
| 描述里列中英文触发语与排除项 | 元数据决定触发，边界避免误命中 |
| 正文只有 6 步 + 3 条错误处理 | 核心流程留在 `SKILL.md`，保持精简 |
| 格式细则放 `references/` | 渐进式披露，避免正文膨胀 |
| 提交提取写成脚本 | 确定性、可重复、不占上下文 |
| 模板放 `assets/` | 用于产出而非阅读 |
| 正文显式列出三个资源 | 让 AI 知道资源存在及使用时机 |
| 明确「失败即停止、不臆造」 | 把易错点写成非显然的领域知识 |

---

## 从这里改造成自己的 Skill

1. 换掉 `name` / 目录名（保持 hyphen-case 一致）。
2. 把 `description` 里的能力和触发说法换成自己业务的真实说法。
3. 把 `Workflow` 的步骤换成自己从零做一次的完整顺序。
4. 问一遍：哪些步骤该抽成脚本？哪些细则该进 references？产出有没有固定模板？
5. 跑校验 → 用 3 句真实请求实测 → 按卡点迭代。
