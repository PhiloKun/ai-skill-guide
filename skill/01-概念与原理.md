# 01 · 概念与原理：AI 的 Skill 到底是什么

## 1. 一句话定义

**Skill（技能）是一个模块化、自包含的能力包**，通过提供专门的知识、工作流程和工具，把通用 AI 助手变成某个领域的「熟练工」。

可以把它理解成给新同事的**入职手册 + 工具箱**：

| 类比 | 对应到 Skill |
| --- | --- |
| 岗位说明书 | `SKILL.md` 的 frontmatter：说明「我是谁、什么时候该找我」 |
| 标准作业流程 SOP | `SKILL.md` 正文：分步骤告诉 AI 怎么做 |
| 工具 / 脚本 | `scripts/`：稳定、可重复执行的程序 |
| 内部资料库 | `references/`：需要时再翻的规范、schema、API 文档 |
| 表格 / 模板 / 素材 | `assets/`：直接拿来产出结果的文件 |

关键点：**Skill 不修改模型权重，也不是运行时插件**，它是一份被按需加载进上下文的结构化指令与资源。

---

## 2. 为什么需要它：三个真实痛点

| 痛点 | 没有 Skill | 有了 Skill |
| --- | --- | --- |
| 模型不知道你的私有知识 | 每次都要在对话里粘贴团队规范、表结构、发布流程 | 知识固化在技能包里，自动按需出现 |
| 长提示词难维护 | 复制粘贴容易漏、容易版本不一致 | 单一文件修改，所有对话立即生效 |
| 上下文窗口有限 | 把所有资料一次性塞进去，浪费 token 且干扰判断 | 三层按需加载，只带当前用得上的内容 |

一句话：**Skill 把「每次都要重新解释」变成「一次编写、按需复用」**。

---

## 3. 物理结构

```text
skill-name/
├── SKILL.md                 # 必需
│   ├── YAML frontmatter     # 必需：至少 name + description
│   └── Markdown 指令         # 必需：目的 / 何时用 / 怎么用
├── scripts/                 # 可选：可执行代码（Python / Bash / …）
├── references/              # 可选：按需加载进上下文的文档
└── assets/                  # 可选：用于最终产出的模板、图片、字体、样板代码
```

- `SKILL.md` 是唯一必需文件；资源目录按需要保留，用不到的直接删掉。
- 目录名通常与 `name` 完全一致，且使用 hyphen-case（小写字母、数字、连字符）。

### `SKILL.md` 的最小形态（真实可用）

```yaml
---
name: changelog-helper
description: Generate a changelog from git history. This skill should be used when users ask to write release notes, summarize commits, or prepare a version changelog.
---

# Changelog Helper

## Overview
Generate a structured changelog from the repository's git history.

## Steps
1. Read the commit range provided by the user.
2. Group commits by type (feature, fix, docs, chore).
3. Write the result in Markdown, newest version first.
```

- `---` 之间是 **YAML frontmatter**，属于元数据，决定是否触发。
- `---` 之后是 **Markdown 正文**，属于操作指令，决定触发后怎么做。

---

## 4. 核心机制：渐进式披露（Progressive Disclosure）

Skill 用三层加载来节省上下文：

| 层级 | 内容 | 何时进入上下文 | 体量建议 |
| --- | --- | --- | --- |
| ① 元数据 | `name` + `description` | **始终**在上下文中 | 约 100 词以内 |
| ② 正文 | `SKILL.md` 的 Markdown 部分 | 技能被触发时 | 建议 < 5k 词 |
| ③ 附带资源 | `scripts/` `references/` `assets/` | AI 判断需要时才读取 / 执行 | 理论上不受限 |

> 之所以「不受限」：脚本可以直接执行而不必读进上下文；长文档可以只读匹配到的片段。

**设计推论**（写 Skill 时最重要的原则）：

1. 元数据写清触发条件，否则第 ② 层永远不会加载。
2. `SKILL.md` 只放**核心流程**，详细资料放 `references/`，避免正文膨胀。
3. 同一份信息只放一处，不要在正文和参考文档里重复。
4. 重复写同一段代码 → 抽成 `scripts/`；重复产出同一份模板 → 放进 `assets/`。

---

## 5. 触发机制

```text
用户输入 → AI 将请求与各技能常驻的 name + description 做语义匹配
        → 命中则加载该技能 SKILL.md 正文
        → 按正文指令执行，并按需引用 scripts / references / assets
```

因此：

- **触发不是靠关键词硬匹配，也不是靠命令**，而是语义判断；但 description 里列出典型说法 / 触发词，能显著提升命中率。
- `description` 是最重要的字段：必须同时回答「它做什么」与「什么时候该用它」。
- 描述太泛（如「帮助写代码」）→ 到处误触发或永远不触发；描述太窄 → 换个说法就漏掉。
- 多个技能描述重叠时，AI 可能选错；应为每个技能划清边界。

参考内置 `lsp-code-analysis` 的写法：描述里带 `Triggers: "find definition", "who calls", ...`，把用户可能说的中英文说法列举出来。

---

## 6. 存放在哪里（作用域）

| 类型 | 路径 | 生效范围 | 适用情况 |
| --- | --- | --- | --- |
| 用户级 | `~/.codebuddy/skills/<name>/` | 所有项目 | 个人工作习惯、通用工具流程 |
| 项目级 | `<项目>/.codebuddy/skills/<name>/` | 该仓库 | 团队规范、项目 schema、共享发布流程 |

不确定时选用户级；需要随 Git 仓库分发给同事时选项目级。

---

## 7. 和相近概念的区别

| 机制 | 本质 | 何时生效 | 适合放什么 |
| --- | --- | --- | --- |
| **Skill** | 自包含的能力包（指令 + 资源） | 语义匹配到才加载 | 领域流程、格式处理、私有知识、模板、脚本 |
| Prompt / 提示词 | 一次性对话输入 | 只在当次对话 | 临时、一次性的要求 |
| Rules / `CODEBUDDY.md` | 常驻约束 | 基本每次都生效 | 「永远要遵守」的硬性规范（如提交流程、代码风格） |
| MCP / 工具服务 | 外部系统与 API 的连接层 | 被调用时 | 真实读写外部数据、调用第三方服务 |
| 脚本 / 工具函数 | 确定性代码 | 显式执行 | 精确计算、格式转换、批量处理 |
| 子代理 Agent | 独立的执行单元与上下文 | 被分派任务时 | 可独立完成的复杂探索 / 评审任务 |

判断口诀：

- **每次都必须遵守** → Rules
- **特定任务才需要的一整套做法** → Skill
- **要连外部系统拿数据** → MCP（Skill 可以在正文里指导如何调用它）
- **一次性的话** → 直接说，不用建文件

---

## 8. 一次完整生命周期

```text
发现（元数据常驻） → 触发（description 命中） → 加载（SKILL.md 正文）
    → 执行（按流程调用脚本 / 查阅 references / 使用 assets）
    → 产出结果 → 观察卡点 → 迭代 SKILL.md 或资源
```

---

## 9. 小结

> Skill = **元数据（决定何时用） + 指令（决定怎么做） + 可选资源（脚本 / 资料 / 模板）**，通过渐进式披露按需要进入上下文，把通用 AI 变成可复用、可分发、可团队共享的专用能力。
