# 03 · 如何编写 Skill：从 0 到可分发的六步

> 目标：产出一个能被 AI 正确触发、稳定执行、可校验打包的技能目录。

---

## 总流程

```text
Step 1 理解用例 → Step 2 规划资源 → Step 3 初始化目录
    → Step 4 编辑 SKILL.md 与资源 → Step 5 校验 / 打包 → Step 6 实测迭代
```

---

## Step 1 · 用具体例子理解需求

先收集 3～5 个**真实用户会说的话**，而不是先想「这个技能该有哪些功能」。

要问清楚：

- 用户会怎么提出这个需求？（中文 / 英文 / 口语化说法）
- 完整做完一次，需要从零开始哪些步骤？
- 哪些文件类型、命令、系统、术语会出现？
- 边界在哪：哪些请求**不该**由这个技能接？

示例（`release-notes` 技能）：

| 真实说法 | 期望结果 |
| --- | --- |
| 「帮我写这一版的发版说明」 | 从 git 历史生成 Markdown changelog |
| "summarize commits since v0.1.0" | 指定范围生成英文 changelog |
| 「把这次改动整理成更新日志」 | 按团队模板输出 |

这一步的产物：**触发语句清单 + 输入输出定义 + 边界**。

---

## Step 2 · 规划可复用资源

对每个用例问：「这段代码 / 资料 / 模板，是不是每次都要重写一遍？」

| 观察到 | 放进 | 理由 |
| --- | --- | --- |
| 反复重写同一段代码、或要求确定性结果 | `scripts/` | 可直接执行，不必读进上下文，结果稳定 |
| 长规范、schema、API 文档、详细流程 | `references/` | 只在需要时加载，保持 `SKILL.md` 精简 |
| 每次产出都要用的模板、样板、图片、字体 | `assets/` | 用于最终产物，不进入上下文 |
| 只是几句话的核心流程 | `SKILL.md` 正文 | 触发后必须立即可见 |

> 原则：**不重复、不塞满**。同一信息只放一处；详细内容优先放 `references/`，核心流程留在正文。

---

## Step 3 · 初始化目录

推荐用官方初始化脚本，它会自动生成合规的 `SKILL.md` 模板与三类资源示例：

```bash
# macOS / CodeBuddy CN 内置脚本（路径含空格，需加引号）
SKILL_CREATOR="/Applications/CodeBuddy CN.app/Contents/Resources/app/extensions/genie/out/extension/builtin/skill-creator"

python3 "$SKILL_CREATOR/scripts/init_skill.py" release-notes --path ~/.codebuddy/skills
```

命令形态：

```text
python3 scripts/init_skill.py <skill-name> --path <输出目录>
```

生成结果：

```text
<输出目录>/<skill-name>/
├── SKILL.md                       # 带 TODO 占位符的模板
├── scripts/example.py             # 示例脚本（权限 755）
├── references/api_reference.md    # 示例参考文档
└── assets/example_asset.txt       # 示例素材占位
```

**注意（实测差异）**：官方说明文档写 `--path` 可省略、默认生成到 `~/.codebuddy/skills/`；但当前内置脚本的实现要求必须显式传 `--path`。**始终显式指定，最稳妥**。

作用域选择：

| 目的 | `--path` 取值 |
| --- | --- |
| 只有自己用、跨项目生效 | `~/.codebuddy/skills` |
| 随仓库共享给同事 | `<项目>/.codebuddy/skills` |

初始化后：删除用不到的示例文件与目录，并清空所有 TODO 占位内容。

---

## Step 4 · 编辑 `SKILL.md`（最关键）

### 4.1 YAML frontmatter 字段

```yaml
---
name: release-notes
description: Generate release notes from git history. This skill should be used when users ask to write a changelog, summarize commits between tags, or prepare version release notes.
---
```

| 字段 | 必需 | 规则 |
| --- | --- | --- |
| `name` | 是 | hyphen-case：仅小写字母、数字、连字符；不以 `-` 开头 / 结尾；不含连续 `--`；建议 ≤ 40 字符；与目录名一致 |
| `description` | 是 | 说明**做什么 + 什么时候用**；用第三人称（"This skill should be used when…"）；带典型触发说法；不要出现 `<` 或 `>` |
| `license` / `allowed-tools` / `disable` | 否 | 在部分内置技能的 frontmatter 中出现；非通用必填项，不同版本支持度可能不同，使用前先确认 |

编写 `description` 的推荐结构：

```text
<一句话说明能力>。This skill should be used when <具体场景>、<文件类型>、<任务类型>。
Triggers: "<说法 1>", "<说法 2>", "<中文说法>"。
Do not use for <明确排除的场景>。
```

> 模板中的尖括号只是占位说明；实际 `description` 不得包含 `<` / `>`（校验会拒绝），请替换为真实文本。

常见写法（多行描述用 `|`）：

```yaml
description: |
  Generate release notes from git history. This skill should be used when users ask
  to write a changelog, summarize commits between tags, or prepare version release notes.
  Triggers: "写发版说明", "生成 changelog", "summarize commits since v1.0".
```

> **坑**：内置 `quick_validate.py` 会拒绝 `description` 中的 `<` 或 `>` 字符；`description: >` 这种 YAML 折叠写法会被判为含 `>` 而校验失败。需要多行时用 `|`，或写成单行。

### 4.2 Markdown 正文

写作风格（官方要求）：

- 使用**祈使句 / 不定式**，不用第二人称：
  - 推荐：`To generate the changelog, run the collection script.`
  - 避免：`You should run the script.`
- 客观、指令化，把 AI 当成执行者，而不是给用户看的教程。
- 只写「对另一个 AI 有用且非显然」的信息，不写常识。

正文必须回答三个问题：

1. **目的**：这个技能让 AI 能做成什么（1～2 句）
2. **何时使用**：哪些请求该走这个流程、哪些不该
3. **怎么用**：完整步骤，并**显式引用所有附带资源**，让 AI 知道它们的存在和读取时机

四种常见组织模式（可混用）：

| 模式 | 适合 | 典型结构 |
| --- | --- | --- |
| Workflow-Based 流程型 | 有明确先后顺序 | Overview → 决策树 → Step 1 → Step 2 |
| Task-Based 任务型 | 一个技能提供多种操作 | Quick Start → 任务 A → 任务 B |
| Reference / Guidelines 规范型 | 品牌 / 编码 / 合规规范 | Guidelines → Specifications → Usage |
| Capabilities-Based 能力型 | 多个相互关联的功能 | Core Capabilities → 1 → 2 → 3 |

篇幅与维护：

- 正文建议 **< 5k 词**；长资料移入 `references/`。
- 参考文档超过 1 万词时，在 `SKILL.md` 里写明可用的 grep 搜索模式，便于按需定位。
- 同一信息**不要在正文和 references 里重复**。
- 删除初始化模板里的 `Structuring This Skill` 说明段和所有 `[TODO:]`。

### 4.3 附带资源写法

- `scripts/`：写明**何时调用、参数、输出格式、失败时怎么办**；脚本给可执行权限，路径用相对技能目录的写法。
- `references/`：写明**什么情况下读哪个文件**；正文中给出相对路径。
- `assets/`：写明**复制 / 修改哪个模板产出结果**；不要把素材内容粘进正文。

## Step 5 · 校验与打包

```bash
SKILL_CREATOR="/Applications/CodeBuddy CN.app/Contents/Resources/app/extensions/genie/out/extension/builtin/skill-creator"

# 只校验
python3 "$SKILL_CREATOR/scripts/quick_validate.py" ~/.codebuddy/skills/release-notes

# 校验 + 打包（校验失败则不会生成 zip）
python3 "$SKILL_CREATOR/scripts/package_skill.py" ~/.codebuddy/skills/release-notes ./dist
```

内置 `quick_validate.py` 实际检查项：

| 检查 | 失败提示要点 |
| --- | --- |
| `SKILL.md` 存在 | `SKILL.md not found` |
| 文件以 `---` 开头且 frontmatter 闭合 | `No YAML frontmatter found` / `Invalid frontmatter format` |
| 含 `name:` | `Missing 'name' in frontmatter` |
| 含 `description:` | `Missing 'description' in frontmatter` |
| `name` 匹配 `^[a-z0-9-]+$`，无首尾 `-`、无 `--` | `should be hyphen-case` |
| `description` 不含 `<` / `>` | `cannot contain angle brackets` |

打包成功后生成 `./dist/<目录名>.zip`，保持目录结构，可直接分发给同事解压到对应 skills 目录。

> `package_skill.py` 依赖同目录的 `quick_validate.py`，两个脚本需放在一起。

## Step 6 · 实测与迭代

1. 用 Step 1 收集的**每一句触发语**真实跑一遍。
2. 记录卡点：没触发 / 触发错技能 / 漏读资源 / 步骤执行错 / 输出格式不对。
3. 按卡点定位修改：
   - 没触发 → 改 `description`（补触发说法、收窄边界）
   - 正文太长或跑偏 → 精简步骤、把细节移到 `references/`
   - 结果不稳定 → 把易错环节抽成 `scripts/`
   - 输出不合规 → 在 `assets/` 固定模板
4. 重新校验 → 再测。技能是「用出来的」，不是「写完就算」。

---

## 编写检查清单

- [ ] 收集了至少 3 个真实触发语句，并明确排除场景
- [ ] `SKILL.md` 存在，frontmatter 以 `---` 正确闭合
- [ ] `name` 为 hyphen-case、与目录名一致、无大写 / 下划线
- [ ] `description` 第三人称，含「做什么 + 何时用 + 触发说法」，无 `<` `>` 与 `[TODO]`
- [ ] 正文为祈使句，回答了目的 / 何时用 / 怎么用
- [ ] 所有 `scripts/` `references/` `assets/` 都被正文显式引用
- [ ] 无重复信息、无未删除的示例文件、正文精简
- [ ] 脚本可执行、路径不写死本机绝对路径
- [ ] `quick_validate.py` 通过；需要分发时 `package_skill.py` 成功
- [ ] 已用真实请求验证触发与输出

## 常见坑速览

| 坑 | 后果 | 修复 |
| --- | --- | --- |
| `description` 写成「帮助处理文档」 | 几乎不触发或到处误触发 | 写具体场景 + 触发说法 + 排除项 |
| 正文塞进整份 API 文档 | 上下文膨胀、指令被稀释 | 移到 `references/`，正文只留引用与 grep 模式 |
| 同一规范在正文和 references 各写一份 | 改动后互相矛盾 | 单一真源 |
| `[TODO:]`、示例占位文件没删 | 校验虽可能通过，但执行时被模板文字干扰 | 初始化后清理干净 |
| `name` 用驼峰 / 下划线 / 中文 | 校验失败 | 改 hyphen-case |
| 把技能放在普通文档目录 | 永远不会被加载 | 放到 `~/.codebuddy/skills/` 或 `.codebuddy/skills/` |
| `description: >` 折叠写法 | 校验报尖括号错误 | 改用 `|` 或单行 |
| 省略 `--path` | 当前脚本直接打印用法并退出 | 显式传 `--path` |
| 脚本路径写死本机绝对路径 | 换机器失效 | 用相对路径或运行时解析 |
