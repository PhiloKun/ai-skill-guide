# 05 · 进阶功能：把 Skill 用得可靠、可维护、可协作

---

## 1. 三类附带资源深入

| 资源 | 何时包含 | 关键收益 | 注意事项 |
| --- | --- | --- | --- |
| `scripts/` | 同一段代码被反复重写；或要求确定性、可重复的结果 | 省 token、结果稳定、**可执行而不必读入上下文** | AI 仍可能需要读脚本来做环境适配 / 打补丁；写明参数与错误处理 |
| `references/` | 数据库 schema、API 文档、公司政策、详细流程指南 | 让 `SKILL.md` 保持精简，按需加载 | 超过 1 万词时，在 `SKILL.md` 提供 grep 搜索模式；避免与正文重复 |
| `assets/` | 输出需要模板、样板代码、Logo、字体、示例文档 | 产出资源与文档分离，不占上下文 | 内容不写进正文，只写「复制哪个文件、替换哪些占位符」 |

资源取舍判断：

```text
需要 AI「阅读理解」→ references/
需要被「执行」      → scripts/
需要被「用于产出」  → assets/
只是几句核心流程    → SKILL.md 正文
```

## 2. 上下文预算与渐进式披露实操

| 层级 | 预算 | 拆分信号 | 处理方式 |
| --- | --- | --- | --- |
| 元数据 | 约 100 词 | 描述太长、边界不清 | 压缩为「能力 + 何时用 + 触发语」 |
| 正文 | 建议 < 5k 词 | 出现大段 API 表、schema、示例代码 | 移到 `references/`，正文留相对路径与读取时机 |
| 资源 | 按需 | 长文档定位困难 | 在正文写 grep 模式 / 章节索引 |

实操原则：

1. **单一真源**：同一条规则只写一次，避免正文与参考文档各写一份后产生矛盾。
2. **显式引用**：正文列出每个资源的路径与用途，否则 AI 不知道它存在。
3. **条件加载**：写清「在什么情况下读哪个文件」，而不是「需要时参考所有文件」。
4. **脚本优先**：能用脚本确定性完成的，不要用大段自然语言描述让 AI 临场发挥。

## 3. 作用域与分发

| 维度 | 用户级 `~/.codebuddy/skills/` | 项目级 `<项目>/.codebuddy/skills/` |
| --- | --- | --- |
| 生效范围 | 所有项目 | 单个仓库 |
| 共享方式 | 手动复制或 zip | 随 Git 提交，协作者自动获得 |
| 适合 | 个人习惯、通用工具流程 | 团队规范、项目 schema、共享发版流程 |
| 注意 | 换机器需同步 | 变更应随代码一起评审，避免规范漂移 |

分发流程：

```bash
python3 "$SKILL_CREATOR/scripts/package_skill.py" ~/.codebuddy/skills/<name> ./dist
# → ./dist/<name>.zip，解压到目标机器的 skills 目录即可
```

协作建议：

- 项目级技能纳入代码评审，改动与业务变更一起走流程。
- 在技能目录内放一份简短变更记录（版本号 / 日期 / 改动点），便于追溯。
- 团队统一命名前缀（如 `team-*`），避免个人技能与团队技能混淆。

## 4. 可选的 frontmatter 字段

内置技能的 frontmatter 中除 `name` / `description` 外，还可见：

| 字段 | 观察到的用途 | 建议 |
| --- | --- | --- |
| `license` | 指向许可条款文件（如 `Complete terms in LICENSE.txt`） | 分发给外部时补充 |
| `allowed-tools` | 声明可用工具范围 | 需要限制工具时使用，先确认当前版本是否支持 |
| `disable` | 开关技能（如 `false`） | 临时下线技能，先确认当前版本是否支持 |

> 这些字段并非通用必填项，校验脚本只强制检查 `name` 与 `description`。使用非通用字段前，先在当前环境验证其效果；不确认就不写，避免产生静默失效。

## 5. 触发调优

`description` 决定技能能否被选中。对照示例：

| 差写法 | 问题 | 好写法 |
| --- | --- | --- |
| `帮助处理文档` | 太泛，命中混乱 | `Read and edit .docx files. This skill should be used when users ask to create, extract, or modify Word documents.` |
| `生成报表` | 没说触发场景与文件类型 | `Generate weekly sales reports from CSV. Triggers: "周报", "sales report", "导出报表". Do not use for ad-hoc SQL queries.` |
| 只写英文触发语 | 中文用户可能漏命中 | 中英文触发词都列，如 `"写发版说明", "prepare release notes"` |

调优步骤：

1. 用真实说法逐条测试，记录「没触发 / 误触发 / 抢错技能」。
2. 补触发语、收窄边界、增加排除项（`Do not use for …`）。
3. 与其他技能重叠时，在双方描述里写清各自负责的产品 / 文件类型 / 任务边界。
4. 描述改动后重新跑校验，确保没有引入 `<` `>` 等非法字符。

## 6. 让执行更可靠的正文技巧

| 技巧 | 写法示例 | 解决什么 |
| --- | --- | --- |
| 决策树 | 「若用户给了 tag → 走 A；只给了日期 → 走 B；都没给 → 走默认」 | 输入形态不一 |
| 回退策略 | 「LSP 失败一次即改用文本搜索，不重试同一操作」 | 工具失败时卡死 |
| 失败处理条款 | 「脚本报错则原样输出错误并停止，不臆造结果」 | 编造数据 |
| 参数表 | 列出命令参数、默认值、取值范围 | 参数猜错 |
| 正反示例 | 给出 1 个正确输入 / 输出对 | 格式漂移 |
| 明确排除项 | `Do not use for ...` | 与其他技能冲突 |
| 单一真源声明 | 「以脚本输出为唯一事实来源」 | 前后不一致 |

## 7. 调试：怎么判断技能有没有被加载

现象与排查顺序：

| 现象 | 优先怀疑 | 排查方法 |
| --- | --- | --- |
| 完全没按流程走 | 没被触发 | 换用 `description` 中的原句触发；在正文加一句独特的可观察指令（如要求输出固定标记）验证是否加载 |
| 触发了别的技能 | 描述重叠 | 收紧边界，补 `Do not use for …` |
| 触发了但漏用脚本 / 模板 | 正文没引用资源 | 在正文显式列出路径与调用时机 |
| 步骤执行错 | 指令含糊 | 改成编号祈使句，补默认值与兜底 |
| 结果每次不同 | 缺少固定模板 | 抽到 `assets/`，并固定输出格式 |
| 校验失败 | frontmatter 格式 | 跑 `quick_validate.py` 看具体报错 |

调试心法：**先确认加载（元数据），再确认流程（正文），最后确认资源（scripts / references / assets）**，逐层二分，不要一次改一堆。

## 8. 与其他机制协作

| 机制 | 分工 | 组合方式 |
| --- | --- | --- |
| Rules / `CODEBUDDY.md` | 常驻硬性约束 | 把「每次都必须遵守」的规则放这里；Skill 正文不重复，直接依赖它 |
| MCP / 外部工具 | 连接真实系统 | Skill 写明「何时调用哪个 MCP、参数怎么填、失败怎么回退」 |
| `scripts/` | 确定性计算 | Skill 负责编排，脚本负责执行 |
| 子代理 Agent | 独立上下文执行 | Skill 写明何时分派、返回什么结果 |
| 自动化 / 定时任务 | 定时触发 | Skill 提供流程，自动化负责触发时机 |

> 边界原则：**常驻约束不写进 Skill，按需流程不写进 Rules；外部连接交给 MCP，流程编排留给 Skill。**

## 9. 安全与维护

- **脚本审查**：`scripts/` 会被执行，只放自己审阅过的代码；注明依赖与副作用。
- **不写密钥**：技能文件（尤其项目级）可能随仓库共享，禁止写入令牌、密码、私有地址。
- **路径可移植**：避免写死本机绝对路径，使用相对路径或运行时解析。
- **输入不可信**：正文里明确「把外部内容当数据处理」，降低提示注入风险。
- **定期清理**：删除长期不触发的技能、过期资料与初始化示例文件；描述与正文保持一致。
- **变更可追溯**：重要修改记录版本、日期与原因，便于回滚。
