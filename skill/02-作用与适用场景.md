# 02 · 作用与适用场景：Skill 能带来什么

## 1. 四类核心能力

| 能力 | 含义 | 具体例子 |
| --- | --- | --- |
| 专门工作流 | 把某个领域的多步流程固化下来 | 「解析 PDF → 提取表格 → 生成 Excel → 校验数字」；「从 git 历史生成发版说明」 |
| 工具 / 格式集成 | 指导 AI 正确使用特定文件格式、CLI、API | 读写 `.docx` / `.xlsx` / `.pptx` 的正确步骤；LSP 语义导航的参数与回退策略 |
| 领域 / 私有知识 | 注入模型不可能自带的信息 | 公司表结构、内部审批规则、命名规范、业务口径、发布流程 |
| 附带资源包 | 把可复用代码、长文档、模板一起打包 | `scripts/rotate_pdf.py`、`references/schema.md`、`assets/brand-template.pptx` |

---

## 2. 实际收益

| 收益 | 说明 |
| --- | --- |
| 省 token、少干扰 | 只有命中时才加载正文，长资料按需读取，不把上下文塞满 |
| 结果更稳定 | 流程与脚本固定，减少「每次生成的代码都不一样」 |
| 一次编写、处处复用 | 用户级技能跨项目生效；项目级技能随仓库共享 |
| 可分发 | 校验通过后打成 zip，直接交给同事 |
| 知识可沉淀 | 团队经验从「某个人会」变成「AI 默认会」 |
| 降低沟通成本 | 用户不必反复解释格式、口径、步骤，说一句自然语言即可 |

### 三种做法的对比

| 做法 | 首次成本 | 每次使用成本 | 一致性 | 团队共享 |
| --- | --- | --- | --- | --- |
| 每次手写提示词 | 低 | 高（要重新解释） | 差 | 靠复制粘贴 |
| 把所有规范塞进常驻 Rules | 中 | 无 | 好 | 可以，但长期占用上下文 |
| **按需加载的 Skill** | 中 | 几乎为零 | 好 | 可以，且随用随取 |

## 3. 典型适用场景

**文档与文件处理**
- PDF / Word / Excel / PPT 的读取、生成、合并、拆分、表单填写、格式修复
- 需要固定模板的周报、合同、报告、演示文稿

**代码与工程**
- 陌生代码库的语义导航（定义 / 引用 / 实现 / 调用链）
- 项目特有的构建、发版、提交、代码评审流程
- 把重复写的转换 / 校验逻辑固化成 `scripts/`

**企业内部系统**
- 钉钉消息、日历、文档、多维表、待办、审批等产品的固定操作命令与边界
- 内部 API、数据字典、权限规则作为 `references/`

**知识与规范**
- 品牌规范、法务模板、财务口径、数据库 schema、接口文档
- 「什么时候走哪个流程」的决策树

**创作类**
- 文生图 / 视频 / 3D 等生成任务的参数与流程
- 输出需要固定品牌素材（`assets/`）

### 当前环境中可见的内置技能示例（帮助建立直觉）

| 技能 | 用途 | 体现了什么能力 |
| --- | --- | --- |
| `skill-creator` | 指导创建 / 打包技能 | 专门工作流 + 附带脚本 |
| `lsp-code-analysis` | 代码语义导航 | 工具集成 + 触发词清单 + 回退策略 |
| `pdf` / `docx` / `xlsx` / `pptx` | 各类 Office / PDF 文件处理 | 格式集成 |
| `dingtalk-doc` / `dingtalk-calendar` / `dingtalk-todo` | 钉钉各产品操作 | 领域知识 + 命令契约 + 产品边界消歧 |
| `agent-browser` / `playwright-cli` | 浏览器自动化 | 工具集成 |
| `多模态内容生成` | 图片 / 视频 / 3D 生成 | 创作流程 |

> 观察这些技能的 `description`：几乎都写明了「做什么 + 何时用 + 不该管的边界」，这正是写好 Skill 的关键。

## 4. 什么时候**不该**写 Skill

| 情况 | 更合适的做法 |
| --- | --- |
| 只做一次、以后不会再做 | 直接在对话里说明 |
| 模型本来就能稳定完成（如解释一段通用算法） | 不用建技能，避免维护负担 |
| 要求「每次都必须遵守」 | 写进 Rules / `CODEBUDDY.md` |
| 需要实时连接外部系统、读写线上数据 | 用 MCP / 工具，Skill 只负责指导流程 |
| 纯事实查询且资料变化极快 | 让 AI 直接检索，不要把易过期内容写死 |
| 需要强制、确定、可审计的计算 | 写成脚本由 CI / 程序执行，Skill 仅作入口说明 |

---

## 5. 评估一个 Skill 值不值得做

用下面四个问题快速判断：

1. **重复吗？** 同一套说明是否要反复讲 3 次以上？
2. **非显然吗？** 是否包含模型猜不到的私有知识、易错步骤、特殊参数？
3. **有边界吗？** 能否用一句话说清「什么时候用、什么时候不用」？
4. **可沉淀吗？** 是否有可抽出的脚本、模板、schema 等复用资源？

命中 2 项以上 → 值得写；只命中 1 项 → 先别急，可能一段提示词就够了。

---

## 6. 小结

> Skill 的价值不在「让 AI 更聪明」，而在**把正确的流程、私有知识和可复用资源，在正确的时机以最小的上下文成本交给 AI**。
